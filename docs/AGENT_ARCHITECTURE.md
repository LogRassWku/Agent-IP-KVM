# Agent 接入边界与实施顺序

本文档记录 Agent 正式接入前的架构决定。它把“会思考的模型”和“能直接控制电脑的执行器”分开，避免模型输出直接变成不可审计的键盘、鼠标或 BIOS 操作。

## 1. 两个 Agent 的职责

| 组件 | 主要职责 | 可以做什么 | 不应独立决定什么 |
|---|---|---|---|
| PC Agent | 已启动操作系统内的理解、规划和系统信息查询 | 读取经授权的主机清单，分析日志，查询网络资料，生成步骤和风险说明 | 绕过板端策略发送 HID，直接改分区、固件或 BIOS |
| KVM Agent | 开发板上的可信执行与恢复控制器 | 读取按需截图，识别约定的 BIOS／UEFI 状态，执行受限 HID 动作，验证结果并在异常时停止 | 自行批准高风险动作，执行任意 Shell 或任意按键序列 |
| 策略与审批层 | 统一决定是否允许动作 | 绑定目标、证据、风险、批准和回滚信息；记录审计事件 | 把“进入 Agent 模式”当作高风险操作批准 |

PC Agent 可以提出“进入 BIOS 并修改某项”的计划，再把其中必须经过视频和 HID 的步骤交给 KVM Agent。KVM Agent 即使收到 PC Agent 的建议，也必须重新检查当前画面、目标身份和用户批准凭据。

## 2. Agent 如何看见画面

KVM 模式继续提供给用户的实时 MJPEG 画面。进入 Agent 模式后停止这条连续浏览器视频流，采集后端保留按需取一帧的能力：

1. 任务开始时取得一张基线截图；
2. 发送一个受限动作；
3. 等待界面稳定或超时，再取得一张截图；
4. 用画面变化、OCR 或固定界面识别结果验证动作；
5. 结果不符合预期就暂停并请求用户处理。

空闲时每秒约 0.2 至 2 次观察已经足够，快速变化阶段才短暂提高频率。因此板端不需要一直解码 30/60 fps 的视频。第一阶段可以使用传统图像差异和 OCR；需要语义理解时，再把经过用户同意的单张截图交给 PC Agent 或远程视觉模型。

## 3. Agent 如何使用 HID

模型只生成结构化动作，例如 `tap("f2")`、`chord(["ctrl", "alt", "delete"])`、`type("text")`、`pointer(0.5, 0.5)` 和 `wait(2)`。板端将这些动作映射到统一 HID 适配器，并执行以下检查：

- 当前模式必须是 Agent，控制租约必须属于当前用户；
- 动作必须在允许的键、鼠标按钮和坐标范围内；
- 每个动作有超时，结束时释放所有按键和鼠标按钮；
- 动作前后保存截图摘要和 HID 报告摘要；
- 屏幕变化与预期不符、设备断开或目标身份改变时立即停止。

这条链路也适用于 BIOS：小模型不需要自由发挥，只需在固定页面和有限动作模板中完成状态匹配。任何无法确定的画面都返回“未知”，不会通过猜按键继续执行。

## 4. 联网查询边界

联网查询由独立的网络工具完成，和 HID 执行器隔离。工具应保存查询来源、时间和摘要；网页内容只能作为参考证据，不能直接变成执行命令。上传截图、主机清单或日志前，界面显示数据内容、目的地和用途，并取得用户批准。没有网络或用户拒绝时，Agent 仍能使用本地缓存和离线规则完成只读诊断。

## 5. 用户审批分级

| 风险级别 | 示例 | 默认行为 |
|---|---|---|
| 只读 | 查看主机清单、读取 BIOS 页面、比较截图 | 可自动执行并记录 |
| 可逆低风险 | 打开设置、输入一段普通文本、切换显示模式 | 会话内首次请求时提示，可按会话授权 |
| 高风险 | 安装程序、重启、修改启动项、写分区、改变安全启动 | 每次动作前显示审批卡，批准后才执行 |
| 不可逆或恢复困难 | 刷写固件、清盘、修改 BIOS 核心安全设置 | 默认拒绝；需要用户明确批准、恢复介质和现场可见证据 |

审批卡至少显示：目标主机、拟执行动作、原因、所依据的截图或系统信息、预期结果、可能影响、回滚方法和批准有效期。批准应绑定动作计划和当前证据摘要，画面或目标改变后自动失效。

## 6. 当前首版实现

1. `GET /api/video/snapshot.jpg` 可以从正在运行的视频流取最近一帧；Agent 模式释放连续流后，会临时打开采集源取得一帧并立即关闭。首版只可靠识别模拟测试图，真实 HDMI 帧保守返回 `unknown`，后续接 OCR 和界面分类器。
2. `POST /api/agent/plans` 只接受白名单结构化动作。只读观察可以直接执行；键盘动作及 BIOS、安装、磁盘等任务进入审批状态，批准摘要和原计划不一致时拒绝执行。
3. Web 审批卡显示风险、动作、状态和计划摘要。执行过程写入 `data/audit.jsonl`，动作后重新取帧并记录校验摘要，日志不保存截图内容。
4. 可选 PC Agent 通过 Bearer 配对令牌向 `POST /api/pc-agent/suggestions` 提交建议、步骤和资料来源。建议只进入缓存，不能直接调用 HID；被控端信息上报在启用令牌后也使用同一认证。
5. 模拟视频、模拟 HID、审批状态机、动作后观察、令牌拒绝和建议缓存已经组成自动化闭环测试。真实 BIOS 页面分类、控制者租约、紧急停止界面和模型运行器仍需继续实现。
6. RDK X5 继续以 Qwen2.5-1.5B-Instruct Q4_K_M 作为计划中的首个本地模型。规则规划器继续作为离线安全基线。
7. DeepSeek 远程模型通过 OpenAI 兼容的工具调用接口接入受限工具循环。它可以读取最新主机清单、查询 KVM/HID 状态、请求按需截图，或提出由审批层接管的 HID 动作计划；它不能直接持有 HID 设备、运行任意 Shell 或跳过审批。
8. 远程系统提示词明确区分缓存主机信息、实时链路状态、当前截图、建议、等待审批和已执行结果。模型被要求在询问当前屏幕时实际调用截图工具，不能根据旧对话猜测。
9. 当前截图工具只返回帧元数据和现有识别器结果。真实 HDMI 画面在没有 OCR／视觉模型时仍可能返回 `unknown`；工具调用成功不能被表述为已经理解画面内容。

## 7. 推荐的首个 Agent 闭环

先不执行 BIOS 写入。用已采集的 `data/controlled-host.json` 和固定的 Windows 桌面截图做一个离线闭环：用户提交任务 → Agent 生成结构化计划 → 页面显示风险与审批卡 → 模拟 HID 动作 → 取得新截图 → 显示验证结果。这个闭环通过后，再把同一套策略接到真实 HID，最后才增加 BIOS 页面识别和可恢复设置任务。

## 8. 无 BIOS 视频时的启动与系统安装

当前 Lenovo 83DF 测试笔记本在 Windows 运行阶段能够通过 UGREEN 25854 输出 HDMI 画面；重启后进入 BIOS，采集卡在 1920×1080@60 和 1280×720@60 均返回 `No Signal`。这证明采集链路在操作系统阶段正常，但不能把 BIOS 黑屏误判为目标已经完成启动。后续测试已将采集参数恢复为 1920×1080@30。

BIOS 视频不可用时，Agent 仍可在目标操作系统运行期间读取和编排启动项，但不能可靠地盲操作固件菜单。Windows 的 `bcdedit /enum firmware /v` 用于读取固件应用；`{fwbootmgr}` 的 `bootsequence` 可设置下一次启动项，`displayorder` 才是持久顺序。`shutdown /r /fw /t 0` 只负责请求下一次进入固件界面，不能代替画面验证。Windows Boot Manager 的 BCD 菜单和 UEFI 的 NVRAM `BootOrder` 必须分别记录和恢复。

系统安装模式采用以下流程：

1. 开发板从专用 USB 存储或独立数据分区读取 ISO，先计算 SHA-256；板端现有只读 Mass Storage 可用于提供安装介质，但不能把正在使用的系统分区直接暴露为可写磁盘。
2. PC Agent 以只读方式采集固件启动项、Secure Boot、BitLocker、ESP、物理磁盘和分区信息，并创建带目标磁盘序列号、镜像摘要和恢复方法的计划。
3. 用户明确批准后，PC Agent 备份 BCD 和当前启动顺序，注册或选择一次性启动项；不能依赖未验证的 `bcdedit /create /application firmware` 语法，也不能覆盖 `\\EFI\\Microsoft\\Boot\\bootmgfw.efi`。
4. 开发板在重启窗口呈现只读虚拟安装介质；HID 只执行白名单动作。安装器尽量使用 Windows unattend 或 Linux autoinstall，减少无画面阶段的交互。
5. 安装完成后验证新系统启动并删除临时启动项；超时、目标身份变化、磁盘布局不符或安装器异常时停止，保留 Windows Boot Manager 作为回退。

如果目标已经运行 Linux，则可在目标系统内使用 `grub-install` 将 GRUB 写入 EFI System Partition，再用 `efibootmgr` 调整 `BootOrder`；应保留 Windows 项并优先使用签名 shim 处理 Secure Boot。开发板是 ARM64，不能直接在板端运行目标 x86_64 的 `grub-install`，这部分必须由目标 PC Agent 或目标的 Linux 启动环境完成。

因此，第一阶段应实现“读取固件启动项 → 生成一次性启动计划 → 备份与回滚”的只读／模拟闭环；在没有固件视频证据时，不允许 Agent 直接执行清盘、分区或永久改变启动顺序。
