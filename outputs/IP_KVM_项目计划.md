# Agent IP KVM 项目计划

更新日期：2026-09-05
状态：阶段 2 的模拟视频 Web 闭环已完成；阶段 3 已完成 HID 能力探测、模拟适配层和离线复合配置计划

## 1. 项目定位

构建一套可部署到多种 Linux 开发板的开源、软硬一体智能 IP KVM。它既提供传统 IP KVM 的看屏幕和键鼠控制，也通过两个能力不同的 Agent 协作，帮助用户完成系统安装、启动故障诊断和 BIOS／UEFI 配置等任务。RDK X5 是首个验证平台，但核心软件不依赖开发板具有 HDMI 输入，而是通过可替换的视频采集适配层接入 UVC、CSI 或其他输入设备。

- **KVM Agent（板端小 Agent）**运行在 RDK X5 上，始终独立于被控电脑的操作系统。它负责采集画面、理解当前阶段、生成有限操作计划、执行键鼠动作、验证结果和保存审计记录。
- **PC Agent（主机端大 Agent）**由用户自愿选择安装。它在操作系统正常运行时读取经过授权的系统状态，提供更完整的诊断、建议和操作计划。
- **用户**拥有最终控制权。涉及 BIOS 写入、磁盘分区、系统安装、删除数据、安全设置和不可逆操作时，必须先看到具体计划并明确批准。

项目拟参加“开源智能硬件解决方案”赛道。主要交付形态为开发板、视频采集、USB HID 控制与双 Agent 软件构成的一体化设备；RDK X5 作为首个参考实现，其他兼容 Linux 开发板可通过硬件适配层加入。

## 2. 核心创新假设

现有方案已经出现硬件级 Computer Use Agent、AI 控制 KVM、自动安装系统等能力，因此“在 KVM 上加入 AI”不能单独作为创新点。本项目计划验证的差异是：

### 2.1 跨越操作系统边界的双 Agent 协作

同一任务根据电脑状态在两种管理平面之间切换：

```text
无系统、BIOS、安装程序、蓝屏或系统失联
                    ↓
             KVM Agent 独立工作

操作系统正常运行且用户已安装 PC Agent
                    ↓
PC Agent 读取系统内状态并提出建议／操作计划
                    ↓
KVM Agent 检查权限、请求必要确认、执行并从画面验证结果
```

PC Agent 提供系统内部的高质量信息，KVM Agent 保留操作系统之外的观察和控制能力。即使 PC Agent 崩溃或系统无法启动，用户仍可退回板端能力。

### 2.2 物理连接约束的临时 PC Agent

PC Agent 是可选组件。用户可以设置 KVM 离开电脑后多久停用和卸载它。连接状态通过带身份验证的周期心跳和租约判断，而不是仅依赖网络是否连通。

到期处理分为两步：

1. **立即失效**：停止接收任务、撤销本次连接凭据并停止服务。
2. **安全卸载**：仅清除安装清单中由本项目创建的程序目录、服务、缓存、临时凭据和日志。

卸载程序不得递归扫描系统盘，不得依据模糊名称删除文件，不得删除用户文档、系统共享组件或其他软件文件。每个可删除对象都必须在安装时登记所有权；无法证明由本项目创建的对象一律保留并报告。卸载前后均生成清单。若卸载失败，保持停用状态，不扩大删除范围。

### 2.3 建议、执行与验证分离

- PC Agent 可以提出建议，但不能绕过 KVM Agent 直接获得硬件控制权。
- KVM Agent 将建议转换为结构化计划，标明目标、动作、风险、预期结果和恢复方法。
- 用户按风险级别授权。
- 每个动作后重新观察屏幕或系统状态，确认结果符合预期后才继续。
- 任何 Agent 不确定当前状态时，应暂停并请求用户处理，不能靠连续试按键碰运气。

## 3. 第一版范围

第一版只证明最小闭环，不直接追求自主安装系统：

1. 取得被控电脑的一张真实画面。
2. 区分 BIOS／UEFI、系统安装界面和已进入操作系统三类状态。
3. 对一个固定 BIOS 页面识别页面名称和当前启动顺序。
4. KVM Agent 生成一份只读说明和建议，不执行修改。
5. 所有判断和用户操作写入本地审计记录。

第一版暂不实现 PC Agent 自动部署、任意 BIOS 导航、磁盘写入、无人值守安装、公网访问和自动自清理。先验证看得见、识别对、说得清，再逐步开放控制能力。

## 4. 总体架构

```text
                           用户浏览器
                    对话、画面、计划、批准、停止
                                │
                                ▼
┌──────────────────── RDK X5 / KVM Agent ────────────────────┐
│ 视频采集 │ 状态识别 │ 任务规划 │ 权限策略 │ HID执行 │ 审计 │
└────┬──────────┬──────────┬──────────┬────────┬─────────────┘
     │ HDMI画面 │          │双向心跳  │        │USB键鼠
     │          │          ▼          │        ▼
     │          │   可选 PC Agent     │    被控电脑 BIOS／安装界面
     │          │ 系统信息、诊断、建议 │
     │          └──────────┬───────────┘
     └─────────────────────┴────────────── 被控电脑
```

模型可以采用两种方式：

- 板上运行轻量模型或规则，负责状态分类、OCR、权限检查和有限任务。
- 经用户配置后调用局域网或云端大模型，负责较复杂的理解和计划。任何外发的截图或系统信息都必须在界面中明确说明。

不能假设 RDK X5 的 10 TOPS BPU 可以直接运行任意语言模型或视觉语言模型；模型需要经过支持性检查、转换和实测。

### 4.1 跨开发板适配边界

- **核心层**：任务、权限、审计、状态机和 Agent 协作协议，不直接访问具体设备节点。
- **视频适配层**：统一暴露设备发现、格式协商、取帧、健康检查和错误状态，首个实现面向 Linux V4L2/UVC。
- **HID 适配层**：统一暴露按键、鼠标、全部释放和紧急停止，具体实现可使用 Linux USB Gadget、外接微控制器或板卡专用接口。
- **加速适配层**：CPU 路径必须可用；RDK BPU、GPU 或其他 NPU 仅作为可选后端。
- **平台描述**：每种板卡用独立配置说明可用接口、设备节点、性能限制和安装步骤，不能把 RDK X5 的路径硬编码到核心逻辑。

## 5. 硬件链路与已知条件

```text
被控电脑 HDMI 输出 → HDMI 线 → USB 视频采集卡 → RDK X5 USB Host
浏览器操作／Agent 动作 → RDK X5 USB Device → USB HID → 被控电脑
```

- RDK X5 板载 HDMI 是输出，不能直接采集另一台电脑的画面。
- HDMI 转 USB 视频采集设备已到货。RDK X5 将其识别为 `Actions Micro Display capture-UVC05`（USB ID `1de1:f115`），Linux `uvcvideo` 驱动可直接使用，无需专用驱动。
- 当前采集卡通过 USB 2.0 High-Speed（480 Mbit/s）枚举，视频节点为 `/dev/video0`，`/dev/video1` 仅提供 UVC 元数据。
- 2026-09-05 初测时，MJPEG 1280×720、30 fps 的驱动缓冲区以约 25 fps 返回，但进一步用原始单帧、FFmpeg 和 OpenCV 复核后确认数据为空，尚不能解码为有效画面；1920×1080、30 fps 和 60 fps 同样没有有效帧。内核在每次采集时记录 `uvcvideo ... Non-zero status (-71)`，表明 USB 视频传输发生协议错误。更换 RDK X5 的 USB Type-A 端口和更换 HDMI 线后现象不变；被控 Windows 电脑也没有检测到采集卡对应的外接显示器，HDMI 热插拔／EDID 握手尚未建立。当前结论是“设备已枚举，视频数据链路未通过”，不能将缓冲区返回速度当作真实帧率。
- 本项目的第二块板已确认为 **D-Robotics RDK X5 V1.0**，运行 Ubuntu 22.04.5 LTS、ARM64、Linux 6.1.83。
- 板端 USB QuickLink 管理链路已验证；具体地址和认证配置仅保存在本地开发环境中，不进入公开仓库。
- 2026-09-05 已完成一次标准系统更新：474 个软件包升级成功，软件包完整性检查和远程管理服务正常。标准升级保留了 19 个涉及编译器、Mesa、网络和 ROS 依赖变化的软件包，暂不执行可能改变依赖关系的完整升级。
- 根分区约 29 GB，更新后已用约 7.9 GB，可用约 20 GB。
- 视频采集与 USB HID 是两个独立方向的链路，分别验证。
- 系统镜像安装最终可能需要 USB 虚拟存储或虚拟光驱能力，第一版不实现。

## 6. 权限与安全模型

### 6.1 动作分级

| 级别 | 示例 | 默认规则 |
|---|---|---|
| 只读 | 识别界面、读取启动顺序、查看设备状态 | 可自动执行并记录 |
| 低风险 | 移动鼠标、切换无写入页面、收集诊断信息 | 用户可选择本次任务授权 |
| 高风险 | 修改 BIOS、改变启动项、安装系统、分区、格式化、删除数据、安全设置 | 每个具体计划执行前必须明确批准 |
| 禁止自动执行 | 绕过认证、关闭安全保护但无法恢复、删除范围无法证明、目标磁盘不明确 | 拒绝执行并说明原因 |

用户批准的是一份具体计划，不是对 Agent 的永久无限授权。计划中的目标、磁盘、镜像、分区或 BIOS 选项发生变化时，原批准失效。

### 6.2 紧急停止与失败处理

- 页面始终提供停止按钮；停止后立即释放所有按键和鼠标按钮。
- 单个动作设定步数和时间上限。
- 画面与预期不一致、PC Agent 与 KVM Agent 判断冲突、连接中断或目标身份变化时立即暂停。
- BIOS 设置在保存前再次展示变更；能够使用“退出且不保存”时优先保留恢复路径。
- 安装系统前必须校验镜像来源和完整性，并再次确认目标磁盘。

### 6.3 PC Agent 安装与退出

- 只能由用户主动选择安装，不因检测到操作系统而静默部署。
- 默认使用普通用户权限；需要管理员权限的单项能力单独申请。
- 安装位置固定，文件所有权通过带校验值的安装清单记录。
- 连接凭据按每台 KVM、每台电脑分别生成，并可撤销。
- 用户可选择“不自动卸载”；若启用自动卸载，可设置断连租约时间。
- 网络短暂中断不能直接触发文件删除。先进入停用状态，确认租约持续过期后才调用受限卸载器。
- 卸载器本身只接受清单内的精确路径和服务标识；越出安装根目录的项目拒绝删除。

- KVM Agent 将 PC Agent 建议和屏幕证据同时展示给用户。

- 选择一个 KVM Agent 容易误判、PC Agent 能提供关键信息的真实任务。
- 对比纯 KVM、纯 PC Agent 和双 Agent 三种方式的成功率、用时、人工确认次数和误操作次数。

完成标准：用实验数据证明双 Agent 协作带来实际改进，而不是仅增加组件。

## 8. 创新验证标准

最终不能只用功能列表证明创新，应至少回答以下问题：

1. PC Agent 提供了哪些 KVM 画面无法取得的信息？
2. 双 Agent 是否比单独的硬件 CUA 降低误操作或缩短任务时间？
3. KVM 被移除后，主机上的权限和凭据是否按用户设置自动失效？
4. 安全卸载是否有文件级差异证明，能够保证不触碰非项目文件？
5. 高风险操作的批准、执行和验证是否可追溯？
6. 操作系统损坏或 PC Agent 不可用时，板端能力是否仍然工作？

如果这些问题没有实测证据，项目只能称为功能组合，不能宣称已经证明创新。

## 9. 每次推进约定

- 每次只选择一个小目标，先说明本次要验证什么。
- 用户未要求继续时，不自动进入下一阶段。
- 不在正在承担其他项目的开发板上安装或修改本项目内容。
- 涉及刷机、底层 USB、磁盘写入、BIOS 写入或 PC Agent 安装时，先准备具体改动和恢复方法。
- 成功后记录实际结果；失败时解决当前阻碍，不顺势扩展范围。
